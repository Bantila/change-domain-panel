# change-domain-panel

Скрипт для смены домена панели, страницы подписки и ноды в инфраструктуре
[Remnawave](https://remna.st), установленной через
[eGamesAPI/remnawave-reverse-proxy](https://github.com/eGamesAPI/remnawave-reverse-proxy)
(nginx-вариант).

Автоматизирует три отдельные операции, которые обычно приходится делать руками:

1. Выпуск нового SSL-сертификата (Cloudflare DNS-01 **или** ACME HTTP-01).
2. Замену старого домена на новый во всех конфигах (`.env`, `docker-compose.yml`, `nginx.conf`).
3. Перезапуск нужных Docker-контейнеров.

Перед изменением файлов скрипт **всегда** делает бэкап и показывает `diff`,
требуя явного подтверждения (`y/N`).

## Что делает скрипт

1. **Проверяет DNS** нового домена — резолвит A-запись и сравнивает с внешним IP
   текущего сервера. Предупреждает, если IP не совпадает (это нормально для
   Cloudflare-прокси на панели/подписке, но **недопустимо** для ноды/ACME HTTP-01).
2. **Выпускает сертификат** одним из двух методов (см. ниже).
3. **Делает бэкап** `.env`, `docker-compose.yml`, `nginx.conf` в
   `<TARGET_DIR>/domain-change-backup-<timestamp>/` перед любыми изменениями.
4. **Ищет старый домен** во всех этих файлах и показывает построчный `diff`
   того, что изменится.
5. **Спрашивает подтверждение** (`y/N`) — без него ничего не применяется.
6. **Заменяет строку домена** (`sed`) во всех найденных файлах.
7. Если в `docker-compose.yml` смонтирован путь к старому сертификату
   (`/etc/letsencrypt/live/<домен>/...`) — обновляет путь на новый сертификат.
8. **Перезапускает контейнеры**, соответствующие выбранной роли
   (`remnawave-nginx`, `remnawave`, `remnawave-subscription-page` или `remnanode`).

## Чего скрипт НЕ делает

- **Не трогает Reality** (`serverNames`, `Host` в Config Profile панели) — это
  меняется отдельно, через API/UI панели. См. раздел [Домен ноды и Reality](#домен-ноды-и-reality).
- **Не удаляет старый сертификат** и не чистит старые DNS-записи в Cloudflare —
  это остаётся на тебе.
- **Не парсит `nginx.conf` построчно** — работает через глобальную замену
  строки домена, а не через понимание синтаксиса nginx. Именно поэтому перед
  применением всегда показывается `diff` — проверяй его.
- **Не угадывает зону Cloudflare** по количеству сегментов домена. Домены вида
  `curt.vltx.eu.cc` ломают наивную эвристику "последние 2 сегмента = зона"
  (реальная зона тут — `vltx.eu.cc`, а не `eu.cc`). Поэтому зона Cloudflare
  указывается явно, скрипт её не вычисляет сам.

## Требования

- Ubuntu/Debian с `bash`, `docker`, `docker compose` (v2).
- Установленный `certbot`. Для Cloudflare-режима — плагин `python3-certbot-dns-cloudflare`:
  ```bash
  apt-get install -y certbot python3-certbot-dns-cloudflare
  ```
- Утилиты `dig`, `curl`, `awk`, `sed`, `grep` (обычно уже есть в базовой системе).
- Root-доступ (`sudo`).
- Установленная Remnawave-инфраструктура в стандартной структуре каталогов
  eGames-скрипта: `.env`, `docker-compose.yml`, `nginx.conf` в одной директории
  (`/opt/remnawave` для панели/подписки, `/opt/remnanode` для ноды).

## Флаги

Для неинтерактивного запуска (автоматизация, CI, cron) все параметры можно
передать флагами. Если хотя бы `--role` не указан — скрипт переходит в
интерактивный режим и спрашивает всё через `read`.

| Флаг | Обязателен | Описание |
|---|---|---|
| `--role panel\|sub\|node` | да (для non-interactive) | Что меняем: домен панели, домен подписки или домен ноды. |
| `--old OLD_DOMAIN` | да | Текущий (старый) домен, который нужно заменить. |
| `--new NEW_DOMAIN` | да | Новый домен, на который переезжаем. |
| `--dir TARGET_DIR` | да | Путь к директории установки (там, где `.env` и `docker-compose.yml`). Обычно `/opt/remnawave` или `/opt/remnanode`. |
| `--cert-method cloudflare\|acme` | да | Метод выпуска сертификата. См. разделы ниже. |
| `--cf-zone-new ZONE` | да, если `--cert-method cloudflare` | Точное имя зоны в Cloudflare для НОВОГО домена (см. [Режим 1](#режим-1-cloudflare-dns-01)). |
| `--cf-zone-old ZONE` | нет | Зона старого домена (зарезервировано, сейчас не используется автоматически — старый сертификат ищется по подстроке пути в `docker-compose.yml`). |
| `--cf-email EMAIL` | нет | Email аккаунта Cloudflare. Если не передан — спросится интерактивно. |
| `--cf-token TOKEN` | нет | API Token или Global API Key Cloudflare. Если не передан — спросится интерактивно (ввод скрыт). |
| `--acme-email EMAIL` | да, если `--cert-method acme` | Email для регистрации в Let's Encrypt (уведомления об истечении сертификата). |
| `--dry-run` | нет | Ничего не применяет и не выпускает сертификат — только показывает, что бы сделал скрипт (проверка DNS, команда certbot, diff файлов). **Рекомендуется всегда запускать первым.** |
| `-h`, `--help` | нет | Показать краткую справку по флагам и выйти. |

### Как определить тип API-ключа Cloudflare

Скрипт сам смотрит на `--cf-token`: если в строке есть заглавные буквы — считает
его API Token (Bearer, современный формат) и использует `dns_cloudflare_api_token`.
Если букв в верхнем регистре нет — трактует как Global API Key и использует пару
`dns_cloudflare_email` + `dns_cloudflare_api_key`. Это эвристика: если у тебя
Global API Key случайно состоит только из строчных символов и цифр, лучше
проверить получившийся `~/.secrets/certbot/cloudflare.ini` вручную.

## Режим 1: Cloudflare DNS-01

```bash
sudo ./change-domain.sh \
  --role panel \
  --old panel.example.com \
  --new new-panel.example.org \
  --cf-zone-new example.org \
  --cert-method cloudflare \
  --dir /opt/remnawave \
  --dry-run
```

**Как работает:**
- Использует `certbot certonly --dns-cloudflare` — проходит DNS-01 challenge
  через Cloudflare API, добавляя временную TXT-запись.
- Выпускает **wildcard**-сертификат сразу на `<zone>` и `*.<zone>` — этого
  сертификата хватит на любые текущие и будущие поддомены этой зоны.
- Не требует, чтобы порт 80 был свободен, и не требует прямого A-record —
  подходит, даже если домен спрятан за Cloudflare-прокси (оранжевое облако).

**Важно про `--cf-zone-new`:** это должно быть ровно то имя зоны, которое
видно в дашборде Cloudflare (`Websites` → сама зона), а **не** механически
взятые последние 2 сегмента домена. Например:

| Домен | Зона в Cloudflare | Неправильная догадка "последние 2 сегмента" |
|---|---|---|
| `sub.example.com` | `example.com` | `example.com` (совпало случайно) |
| `curt.vltx.eu.cc` | `vltx.eu.cc` | `eu.cc` ❌ (это НЕ зона) |

Если указать неправильную зону — DNS-01 challenge не пройдёт (Cloudflare не
найдёт такую зону в твоём аккаунте), либо (если зона случайно существует, но
не та) сертификат выпустится не на тот домен и не покроет твой поддомен.

## Режим 2: ACME HTTP-01

```bash
sudo ./change-domain.sh \
  --role node \
  --old node.example.com \
  --new new-node.example.org \
  --cert-method acme \
  --acme-email you@example.com \
  --dir /opt/remnanode \
  --dry-run
```

**Как работает:**
- Использует `certbot certonly --standalone --http-01-port 80` — Let's Encrypt
  напрямую обращается на порт 80 сервера.
- **Не требует Cloudflare-токена** — подходит для доменов вне Cloudflare.
- **Не поддерживает wildcard** — сертификат выпускается только на конкретный
  `NEW_DOMAIN`, без покрытия других поддоменов.
- **Требует свободный порт 80.** Скрипт сам временно останавливает контейнер
  `remnawave-nginx` (если он слушает порт), выпускает сертификат и сразу
  поднимает контейнер обратно — до общего рестарта на последнем шаге.
- **Требует прямой A-record**, без Cloudflare-прокси. Если IP домена не
  совпадает с IP сервера — скрипт **прерывается с ошибкой** (не просто
  предупреждает, как в Cloudflare-режиме), потому что HTTP-01 challenge
  физически не сможет достучаться до сервера через прокси.
- Временно открывает `ufw allow 80/tcp` на время challenge и закрывает после.

## Интерактивный режим

Запуск без `--role` (или вообще без аргументов) переводит скрипт в
пошаговый диалог:

1. Нода или панель+подписка?
2. Если панель+подписка — домен панели, подписки или оба сразу?
   - При выборе "оба" скрипт явно предупреждает: замена `old → new`
     применяется одинаково везде, где встречается старый домен. Если у
     панели и подписки **разные** домены — нужно запускать скрипт дважды
     (отдельно для каждой роли).
3. Директория установки (с адекватным дефолтом: `/opt/remnawave` или `/opt/remnanode`).
4. Старый и новый домен.
5. Метод сертификата (Cloudflare или ACME), с соответствующими уточняющими вопросами.

Все проверки (совпадение зоны, DNS) выполняются и в интерактивном, и в флаговом режиме одинаково.

## Примеры

### Смена домена панели (Cloudflare, есть wildcard-зона)

```bash
sudo ./change-domain.sh --role panel \
  --old panel.old-domain.ru \
  --new panel.new-domain.com \
  --cf-zone-new new-domain.com \
  --cert-method cloudflare \
  --dir /opt/remnawave \
  --dry-run   # сначала проверь diff
```

Убрать `--dry-run`, когда diff устраивает — команда та же, но выполнится по-настоящему
и попросит финальное `y/N`.

### Смена домена подписки на ту же зону

```bash
sudo ./change-domain.sh --role sub \
  --old sub.old-domain.ru \
  --new sub.new-domain.com \
  --cf-zone-new new-domain.com \
  --cert-method cloudflare \
  --dir /opt/remnawave
```

Если зона `new-domain.com` уже покрыта wildcard-сертификатом с предыдущего
шага (например, ты уже поменял домен панели на ту же зону) — certbot не будет
перевыпускать сертификат, просто переиспользует существующий.

### Смена домена ноды через ACME HTTP-01 (нет Cloudflare)

```bash
sudo ./change-domain.sh --role node \
  --old old-node.ru \
  --new new-node.io \
  --cert-method acme \
  --acme-email admin@new-node.io \
  --dir /opt/remnanode
```

## Как работает замена домена

Скрипт **не парсит** синтаксис `nginx.conf` — вместо этого он находит все
файлы (`.env`, `docker-compose.yml`, `nginx/nginx.conf` или `nginx.conf`),
содержащие точную строку `OLD_DOMAIN`, и заменяет её на `NEW_DOMAIN` через
`sed`. Это работает надёжно независимо от точного синтаксиса файла (домен —
просто строка, встречающаяся в `server_name`, `FRONT_END_DOMAIN=`,
`SUB_PUBLIC_DOMAIN=` и т.д.), но означает, что **нужно смотреть `diff` перед
подтверждением** — если старая строка домена случайно совпадает с чем-то
посторонним (маловероятно, но теоретически возможно), это тоже будет заменено.

Пути к сертификатам в `docker-compose.yml`
(`/etc/letsencrypt/live/<домен>/fullchain.pem` →
`/etc/nginx/ssl/<домен>/fullchain.pem`, монтируемые в контейнер nginx)
обновляются отдельным шагом: скрипт ищет все смонтированные пути вида
`/etc/letsencrypt/live/<что-то>`, проверяет, является ли `OLD_DOMAIN`
этим доменом или его поддоменом, и если да — переключает путь на каталог
нового сертификата.

## Домен ноды и Reality

Смена домена ноды в файловой системе (сертификат + `nginx.conf`/Caddyfile на
самой ноде) — **это только половина дела**. Домен, который клиенты видят в
`vless://` ссылках (Reality `serverNames`, поле `dest`, Host в панели),
хранится **в панели**, не на ноде, и меняется отдельно:

1. Панель → **Config Profile** → нужный VLESS+Reality **Inbound** →
   `realitySettings.serverNames` — заменить на новый домен.
2. Панель → **Hosts** → Host, который смотрит на этот Inbound — обновить
   `address` (если там был домен, а не IP) либо оставить `sni` пустым, тогда
   он подтянется из `serverNames` автоматически.
3. Запушить обновлённый Config Profile на ноду из панели.
4. Убедиться, что `SELF_STEAL_DOMAIN` в `.env` ноды совпадает с
   `serverNames` дословно — иначе Reality handshake или ACME сломаются.

Скрипт `change-domain.sh` при `--role node` только выпускает сертификат и
меняет `.env`/`nginx.conf` **на самой ноде** — про Reality он выводит
предупреждение, но ничего не делает автоматически.

## Восстановление из бэкапа

Перед любыми изменениями файлов скрипт создаёт бэкап:

```
<TARGET_DIR>/domain-change-backup-<YYYYMMDD-HHMMSS>/
  .env.bak
  nginx.conf.bak
  docker-compose.yml.bak   (если был изменён)
```

Откатить вручную:

```bash
cd /opt/remnawave
cp domain-change-backup-20260801-090700/.env.bak .env
cp domain-change-backup-20260801-090700/nginx.conf.bak nginx.conf
docker compose down
docker compose up -d
```

Скрипт не удаляет старые бэкапы автоматически — чисти их сам по мере необходимости.

## Известные ограничения

- Рассчитан именно на структуру каталогов **eGamesAPI/remnawave-reverse-proxy**
  (nginx-вариант: `.env`, `docker-compose.yml`, `nginx.conf` в одной
  директории, контейнер `remnawave-nginx`). Для установок через официальный
  метод remna.st (без этого инсталлятора) структура файлов может отличаться —
  проверяй `diff` внимательнее и, возможно, поправь список `FILES_TO_PATCH`
  в скрипте под свою структуру.
- Не тестировался с Caddy-вариантом eGames-инсталлятора (там вместо
  `nginx.conf` — `Caddyfile`, и логика перевыпуска сертификатов встроена в
  сам Caddy). Для Caddy-установок скрипт в текущем виде не подойдёт без
  доработки.
- `--role both` в интерактивном режиме (и внутренняя роль `panel_and_sub`)
  предполагает, что у панели и подписки **одинаковый** старый и новый домен.
  Для разных доменов запускай скрипт дважды.
- Эвристика распознавания типа Cloudflare-ключа (Token vs Global API Key) по
  наличию заглавных букв — не железобетонная, при сомнениях проверь
  `~/.secrets/certbot/cloudflare.ini` после генерации.

## Диагностика проблем

**`certbot: connection refused` / `Address already in use` (ACME HTTP-01)**
Порт 80 занят чем-то, что скрипт не смог остановить автоматически (не
`remnawave-nginx`, а другой веб-сервер/прокси). Останови его вручную перед
повторным запуском:
```bash
docker compose stop <имя-контейнера>
# или
systemctl stop nginx apache2
```

**`Invalid response from ... 404` (ACME HTTP-01)**
DNS ещё не обновился (проверь `dig +short A NEW_DOMAIN`), либо домен всё ещё
идёт через Cloudflare-прокси — для HTTP-01 нужен прямой (серый) DNS-record.

**`NEW_DOMAIN не является поддоменом зоны CF_ZONE_NEW`**
Проверь точное имя зоны в дашборде Cloudflare — она может отличаться от
интуитивно ожидаемых "последних двух сегментов" домена, особенно для доменов
вида `something.eu.cc`, `something.co.uk` и подобных.

**Сертификат выпустился, но браузер жалуется на TLS**
Проверь, что `docker-compose.yml` монтирует именно новый путь к сертификату
(шаг 4 в логах скрипта — "Найден смонтированный сертификат старого домена…").
Если путь не совпал автоматически — пропиши вручную и `docker compose up -d`.

## Дисклеймер

Скрипт меняет продовую конфигурацию (домены, сертификаты, панель, подписку
или ноду VPN-инфраструктуры). Всегда сначала запускай с `--dry-run`. Автор не
несёт ответственности за даунтайм или потерю данных — перед использованием
на боевом сервере протестируй на staging-окружении, если оно есть.
